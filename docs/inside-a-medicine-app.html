Inside a medicine app

Follow one tap, "I took my 8 AM pill", through every part of an app: what you see, the messenger, the brain, the memory, and the building it all lives in.

One tap, start to finish

The journey of "I took it"

  1. Tap.

    Grandma presses the big "Taken" button. JavaScript on the phone notices.

  2. Request.

    The frontend writes an order slip (a request) and sends it over the internet to an API address.

  3. Check and decide.

    The backend checks the request makes sense and applies the rules, such as "don't count the same dose twice".

  4. Save.

    The backend writes one new row into the database: which medicine, what time, taken.

  5. Reply.

    The backend answers "Saved". The frontend shows a green tick and "Taken at 8:15 am".

Layer 1

Frontend

Runs on the user's phone, in the browser

Everything on the screen: the medicine list, the big "Taken" button, the colours, the text size. It is built with three languages. Think of building a house:

HTML: the wallsWhat is on the page. "A heading, a list of medicines, a button."
CSS: the paintHow it looks. "The button is green, 60px tall, with large text."
JavaScript: the wiringWhat happens. "When tapped, show a tick and send a message."

Because the frontend runs on the user's own device, anyone can see and change it. Important decisions are never trusted to the frontend alone.

Layer 2

API

The agreed language between frontend and backend

An API is a fixed agreement on how the two sides talk, like an order slip the kitchen only accepts in one format. When grandma taps "Taken", the frontend sends a request:

POST /api/doses
{ "medicine": "Metformin", "time": "08:00", "status": "taken" }

and the backend sends back a response:

200 OK
{ "message": "Saved", "takenAt": "08:15" }
MethodMeansIn our app
GETGive me dataShow today's medicines
POSTSave something newI took a pill
PUTChange somethingEdit a dose
DELETERemove somethingStop a medicine

Each reply carries a short status code: 200 means OK, 404 means not found, 500 means the server had a problem.

Layer 3

Backend

Runs on a computer you control

A program that receives every request and decides what to do with it. In our app it has four jobs:

  1. Validation: reject nonsense, such as an empty medicine name or a time like 27:90.
  2. Business logic: the app's rules. Was the dose late? Was it already marked? Has a dose been missed for 30 minutes?
  3. Talking to the database: saving records and fetching them later.
  4. Security: each family only sees its own medicines.

Why not do this on the phone? The phone can be tampered with and the server cannot. And if grandma and her daughter both use the app, they need one shared source of truth.

Database

Layer 5

Hosting

Puts the app on the internet

While we build, the app runs only on your own computer, called localhost. Hosting copies it to an always-on computer in a data centre and gives it a web address.

  • Deploying: uploading the app to the host.
  • Domain: the friendly address people type, like goldendose.app.
  • HTTPS: the padlock. It encrypts traffic, which is essential for health information.
Design for older users

What our field notes told us

UI is how the app looks. UX is how it feels to use. These six needs came from watching a real older person use their phone, and each one becomes a design rule.

Hard to read

Text at least twice normal size. Dark text on a plain light background. A "Read aloud" button speaks the medicine name and dose. A photo of each pill or strip, because people recognise medicine by its look.

Wrong taps

A few big buttons per screen, spaced far apart. Long press and double tap do nothing. Every "Taken" can be undone for a few minutes.

Missed reminders Top priority

A loud, full-screen alarm instead of a small notification. It repeats every few minutes until "Taken" or "Skip", shows the pill photo, and speaks the instruction.

Getting lost

The app is basically one screen: today's medicines in time order. Adding or changing medicines lives in a separate area, ideally run by a family member.

"Did I take it?"

Each finished dose shows a big green tick and the time, such as "Taken at 8:15 am", so a second look answers the question at once.

Calling for help

A caregiver is linked to the app. If a dose is missed for 30 minutes, they get a message. They can also update the medicine list remotely.

Words you will hear

Glossary

Frontend
The part of the app on the user's screen.
Backend
The program on a server that does the real work.
API
The agreed set of requests and responses between them.
Endpoint
One address in the API, such as /api/doses.
JSON
The text format used to package data in requests and responses.
Database
Permanent, organised storage made of tables.
SQL
The language for asking a database questions.
localhost
Your own computer, acting as a server only you can reach.
Deploy
Upload the app to a host so others can use it.
PWA
Progressive Web App: a website that can be installed on a phone's home screen like an app.
Push notification
A message a server sends to a phone even when the app is closed.
