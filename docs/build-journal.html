1

Requirements

What must the app do, and for whom?

What we did
  1. Started from real observation: you wrote down six things an older person struggles with on a phone.
  2. Turned the people into two personas: Kamala (the elder) and Priya (her daughter, the caregiver).
  3. Wrote 16 user stories ("As Kamala, I want…, so that…"), each marked Must, Should or Later.
  4. Turned vague wishes into testable numbers: "big text" became "at least 24px", "big buttons" became "at least 64px tall".
  5. Wrote what we would not build (out of scope), and acceptance criteria in Given / When / Then form.
  6. Recorded the decisions: web app first, then Android and iPhone; caregivers and elders many-to-many; alerts by SMS, WhatsApp or app.
What it produced
docs/REQUIREMENTS.md
Ideas worth remembering
Persona
An imaginary person who stands for your real users. "Would Kamala understand this?" is easier to answer than "would users?"
User story
A requirement written from the user's side: who, what, and why.
Priority
Must / Should / Later. Stops a project from trying to do everything at once.
Non-functional requirement
How well it must work (text size, contrast, works offline), not what it does.
Acceptance criteria
"Given…, when…, then…": how we'll know a feature is finished.
Scope
The edge of the project. Writing down what's out is as useful as what's in.

LessonYour note "reminders are the most important" led to a hidden requirement: the alarm must work without internet. So the schedule is kept on the phone, not only on the server. Requirements work finds problems while they're cheap to fix.

Check yourself
Why write "buttons at least 64px tall" instead of "big buttons"?

Because a number can be tested. In Step 8 a robot measures every button. "Big" means different things to different people.

Who are Kamala and Priya?

Personas, not real people. Kamala stands for the older users; Priya for the family caregivers. Their needs come from your field notes.

2

UX design

How does each person move through the app, and what can go wrong on the way?

What we did
  1. Wrote five user journeys: taking a pill, pressing Taken by mistake, missing the alarm, "did I take it?", and Priya adding a medicine.
  2. For every step asked: what could go wrong, and how does the design prevent it or make it easy to recover?
  3. Drew the screen map. Kamala's side has only two screens: Today and the alarm.
  4. Sketched rough wireframes of the three key screens before choosing any colours.
What it produced
docs/UX-FLOWS.mdwireframes (in our chat)
Ideas worth remembering
UX
User experience: how the app feels to use. UI is how it looks.
User journey
A short story of someone using the app to get one thing done.
Unhappy path
What happens when things go wrong: a mistaken tap, a missed alarm, no internet.
Error prevention
Making mistakes hard: a dose more than an hour away has no Taken button.
Error recovery
Making mistakes cheap: Undo for 5 minutes.
Wireframe
A plain sketch of what goes where, with no colour or polish.
Decisions and why
  • Kamala never sees "missed" in red. It would worry her. She sees "Not taken yet"; Priya sees "Missed", because she has to act.
  • Setup is the caregiver's job. No settings for Kamala to get lost in.
  • The alarm repeats every 5 minutes until Taken or Skip, then alerts the family at 30 minutes.
Check yourself
Why spend time on the "unhappy path"?

Because that's where older users get stuck or frightened. A happy path that works is not enough; a mistaken tap or a missed alarm must be handled calmly.

3

UI design and the prototype

Exactly how does it look, and does it feel right before we build it for real?

What we did
  1. Wrote a design system: one typeface (Atkinson Hyperlegible, made for low vision), named colours, text sizes and button sizes.
  2. Checked every text colour against its background: all at least 7:1 contrast, the strictest level.
  3. Built a clickable prototype in HTML, CSS and JavaScript with made-up data and a pretend clock, so the alarm could be tried without waiting.
  4. You tried it, and we fixed what you found.
What it produced
docs/DESIGN-SYSTEM.mdprototype/index.htmlprototype/styles.cssprototype/app.js
Ideas worth remembering
Design token
A named design value, like --go: #0B5A2F. Change it once, and every screen follows.
Contrast ratio
How much text stands out from its background. 7:1 is the strictest standard (WCAG AAA).
Touch target
The area a finger can hit. Ours are 64–72px, against a common 44–48px.
Prototype
A version that looks and feels real but uses fake data. Cheap to change.
HTML / CSS / JS
The walls, the paint and the wiring of a page.

LessonThe alarm locked scrolling so Kamala couldn't scroll away, but that also hid our testing buttons. Your report found it. Every design decision has side effects, and testing by hand is how you find them.

Check yourself
What is a design token, and why use one?

A named value such as a colour or size. Both apps read the same tokens from shared/tokens.css, so they always match, and a change happens in one place.

Why does the zero in GoldenDose have a slash through it?

The typeface was designed so similar characters (0 and O, 1 and l) look clearly different, which matters for doses and times.

4

Data design

What must the app remember, and how is it organised?

What we did
  1. Listed the things the app must remember, and gave each a table: caregivers, elders, care_links, medicines, schedules, dose_log, devices, notifications.
  2. Gave every row an id, and linked tables with foreign keys (a column holding another table's id).
  3. Used your two "yes" answers to design care_links, a table of caregiver–elder pairs.
  4. Made the database itself refuse a second record for the same dose on the same day.
What it produced
docs/DATA-DESIGN.mdbackend/src/schema.sql (in Step 6)
Ideas worth remembering
Table, row, column
Like a spreadsheet: one table per kind of thing, one row per item, one column per fact.
Primary key (id)
A number that names a row forever.
Foreign key
A column pointing to another table's id: how tables link.
One-to-many
One medicine has many times: Metformin at 08:00 and 20:00.
Many-to-many
Caregivers ↔ elders, both ways. Needs a "join table" in the middle: care_links.
Unique constraint
A rule the database enforces itself: no duplicate dose per day.
Soft delete
A stopped medicine is marked inactive, not erased, so history still makes sense.
Check yourself
Why can't "caregiver" just be one column in the elders table?

Because Kamala can have two caregivers, and Priya can look after two elders. One column holds one value. A table of pairs holds any number.

Why are passwords never stored?

We store a one-way scramble (a hash). Even if the database were stolen, the passwords couldn't be read.

5

API design

Exactly which requests can the screens send, and what comes back?

What we did
  1. Listed about 20 requests in 6 groups: accounts, elders, pairing, medicines, today, history.
  2. For each: the method (GET, POST, PUT, DELETE), the path, an example request and reply, and the error message when it fails.
  3. Decided how callers prove who they are: caregivers sign in; Kamala's phone is paired with a 6-digit code.
  4. Described the background job that checks for missed doses every minute.
What it produced
docs/API-DESIGN.md
Ideas worth remembering
Endpoint
One address in the API, such as /api/doses.
Method
GET = read, POST = create, PUT = change, DELETE = remove.
Status code
200 OK, 201 Created, 204 done with nothing to send, 400 bad request, 401 not signed in, 403 not allowed, 404 not found, 409 conflict.
JSON
The text format for data: { "status": "taken" }.
Token
A long secret sent with every request, like a wristband at an event.
Background job
Work the backend does on its own, on a timer.
Check yourself
What does 409 mean when Kamala taps Taken twice?

Conflict: "already marked as taken at 9:02 am." The second tap is refused, so nothing is counted twice.

Why design the API before writing code?

It's the contract between frontend and backend. With it agreed, both sides can be built separately and still fit together.

6

Backend and database

How do we make the rules real, and keep them safe?

What we did
  1. Set up Git save points, then built the backend with Node.js and Express.
  2. Created the tables in SQLite (one file) from schema.sql.
  3. Wrote one file per group of requests, plus validation (check every input), security (hashed passwords, hashed tokens, "do you look after this person?") and time zones (9:00 means 9:00 where Kamala lives).
  4. Built the missed-dose check: every minute, marks doses 30 minutes late as missed and alerts each caregiver by their chosen channels (simulated for now).
  5. Wrote 33 automatic tests using a pretend clock, and a guided tour script.
What it produced
backend/src/backend/test/api.test.jsbackend/README.md
Ideas worth remembering
Validation
Never trust input. "27:90" is not a time; an empty name is refused with a clear message.
Hashing
A one-way scramble for passwords and tokens.
Transaction
Several changes saved together, or none: a medicine is never saved without its times.
Middleware
Code that runs before every request, such as "who is calling?"
Automated test
A small program that uses the app and checks the result, every time.
Git commit
A snapshot of the whole project you can go back to.

LessonBuilding revealed a gap: a medicine added at 3 pm with an 8 am time would instantly count as "missed". We fixed it, wrote a test for it, and recorded it in the data design. Real building always finds details the plan missed.

Check yourself
Why does the backend check rules that the screens also check?

The screens run on people's phones and can be tampered with. The backend is the one place that can't, so it enforces every rule. The screens check too, only to give quick feedback.

What is the "pretend clock" for?

Tests can jump to 9:30 to check the 30-minute rule without waiting. The same idea as the prototype's "Jump ahead 10 minutes".

7

Frontend

How do the screens use the real backend, and stay kind to their users?

What we did
  1. Turned the approved prototype into Kamala's app: pairing, Today and the alarm, now using real data.
  2. Built Priya's family app: sign in, people, medicines with photos, pairing codes, 7-day history, alert choices, invite family.
  3. Put shared pieces in one folder: design tokens, the API helper, pill drawings.
  4. Made Kamala's app work offline: the last list is saved on the phone; a tap made offline is saved and sent later.
  5. Protected against code injection: every typed name passes through esc().
  6. Tested end to end in the browser: added a medicine, paired a phone, watched the alarm ring at 6:59 pm.
What it produced
frontend/index.htmlfrontend/elder.jsfrontend/care/frontend/shared/
Ideas worth remembering
Single-page app
One page whose content changes with the address after #; the browser never reloads.
XSS
Cross-site scripting: an attack that hides code inside typed text. Escaping text prevents it.
Offline-first
Keep working without internet, and catch up when it returns.
localStorage
A small store in the browser that survives closing the app.
Pairing
Connecting a device with a one-time code instead of a password.

LessonsTesting by hand found three problems: a grey "000000" made the code box look already filled; a failed photo upload could create a duplicate medicine; times wrapped onto two lines. All small, all things a real user would have hit.

Check yourself
What happens if Kamala taps Taken with no internet?

She sees the green tick straight away. The tap is saved on the phone, and sent automatically when the internet returns.

Why can't the web version ring on a locked phone?

Browsers aren't allowed to wake a locked phone. That's why the Android and iPhone apps are a later stage.

8

Testing

How do we prove it works, and that real people can use it?

What we did
  1. Added browser tests with Playwright: a robot uses the real screens on a phone-sized display (20 tests).
  2. Added accessibility scans with axe: Kamala's screens pass the strictest level, WCAG AAA.
  3. Wrote a test plan linking every requirement to the test that proves it.
  4. Wrote a user-testing script for watching a real older person use the app.
  5. Set up the demo: one command, a live API log, a database peek, a demo script and runbook.
What it produced
e2e/docs/TEST-PLAN.mddocs/USER-TESTING.mddocs/DEMO-SCRIPT.md
Ideas worth remembering
End-to-end test
Tests the whole system from screen to database, like a person would.
Accessibility
Usable by people with low vision, shaky hands or screen readers. WCAG is the standard.
Traceability
Every requirement has a test that proves it.
User testing
Watching real people use it, without helping. Finds confusion that no robot can.

LessonThe first run found a real bug: a wrong password on the family sign-in showed no message at all. The code treated it as "sign-in expired" and silently reloaded. Tests find bugs before users do.

Check yourself
What does automatic testing catch, and what does user testing catch?

Automatic tests catch bugs: things that don't work. User testing catches confusion: things that work but are hard to understand. You need both.

How many automatic tests are there, and how do you run them?

56 in total (33 backend, 23 browser and accessibility). From the medstracker folder, run npm test.

9–10

Deploy, then iterate

How does it reach real families, and keep getting better?

What's planned
  • Hosting: run the backend on an always-on server with a real web address and HTTPS.
  • PostgreSQL: the database built for many users at once.
  • Real alerts: SMS and WhatsApp through a messaging provider; app notifications.
  • Security for the open internet: limits on password and pairing-code guessing.
  • Continuous integration: the 56 tests run automatically on every change.
  • Phone apps: the same code wrapped for Android and iPhone, with lock-screen alarms.
  • Iterate: user testing with five people, fix what confuses them, repeat.

Before startingThis stage needs accounts and small monthly costs, so options and prices are compared first, for a decision with your boss.

Explaining GoldenDose to anyone

"GoldenDose helps older people take their medicines and tells their family when they don't. The elder's app is one screen with a loud, full-screen alarm that shows the pill and reads the instruction. The family app sets everything up and gets an alert if a dose is 30 minutes late."

"Behind the scenes, the screens talk to a backend through an API. The backend checks every rule and stores everything in a database. We built it in the order professionals do: requirements from watching a real older person, then design, then data and API plans, then code, then 56 automatic tests. Next, we put it online and test it with real families."
